# API architecture and drawing plan

## Scope and decisions

Keep the App and Carousel concepts. Refactor their responsibilities so the API
can support multiple devices, configurable apps, and reusable drawing utilities.
This document is a plan; implementing it is a separate task.

Use these decisions for the first implementation:

- Keep request-driven rotation: a device requests the next app after displaying
  the previous one. Do not introduce a continuous, time-based schedule.
- Give every device its own ordered playlist and rotation state.
- Register app implementations separately from configured app instances.
- Keep the existing function-based implementations behind a typed adapter.
  Subclassing is not required.
- Put freshness, retries, and output caching in a common runtime.
- Keep Pillow and build a small drawing toolkit over it.
- Start with one API process and in-memory runtime caches. Persist device and
  playlist configuration in SQLite before exposing settings endpoints.
- Keep server credentials in server settings. Store user-facing app settings,
  such as location and subway stations, in validated instance configuration.

## 1. Device playlists and rotation

### Problems

- `main.py` creates one global `AppCarousel`. All clients advance the same index.
- `apps/__init__.py` registers mutable singleton apps, combining implementation,
  configuration, and cached state.
- `Carousel.render_current()` combines selection, fetching, rendering, and
  advancement. Browser previews would unintentionally advance device rotation.
- `enabled` is never checked. An empty playlist fails by indexing an empty list.
- Rotation happens once per request, although the README says it uses TTL.
- Retries advance the carousel again, potentially skipping an app after a failed
  download.

### Fix

Introduce these distinct objects:

| Object | Fields/responsibility |
| --- | --- |
| `AppDefinition` | App type ID, name, configuration model, fetch/render callables, default refresh policy |
| `AppInstance` | Instance ID, app type ID, validated configuration, configuration revision |
| `PlaylistEntry` | Entry ID, instance ID, enabled flag, display duration in seconds; list position determines order |
| `DeviceConfig` | Device ID, display dimensions, ordered playlist, playlist revision |
| `DeviceRotationState` | Current/next entry ID, last request ID, last response bytes and metadata |
| `AppRuntime` | Data/output caches, refresh bookkeeping, failure handling |

An app type can have multiple instances. For example, two weather instances can
use different locations. Rotation belongs to the device, not the app instance.
For the first version, create instances per device; cross-device sharing can be
added later through explicit cache keys.

Move `enabled` and display duration to the playlist entry. Keep the app's data
refresh policy separate. Use stable entry IDs rather than relying on a saved
integer index when a playlist is edited.

### Endpoint and retry contract

Add `POST /api/devices/{device_id}/next` with a JSON `request_id` generated by the
device. Return WebP bytes with these headers:

- `X-App-Instance-Id`
- `X-Display-Duration-Ms`
- `X-Request-Id`
- `Cache-Control: no-store`

The device generates a new request ID for each intended advancement. It retries
with the same ID until the image has downloaded, decoded, and been accepted for
display. It must not generate a new ID merely because an HTTP request failed.

Process requests under a per-device lock:

1. If the ID matches the last completed request, return the saved response
   unchanged. Do not refresh its data, regenerate its bytes, or advance again.
2. Select the next enabled entry using the device's playlist snapshot.
3. Ask the app runtime for displayable content. Skip entries that explicitly
   report unavailable content or cannot produce a usable frame.
4. Try each enabled entry at most once. If none is usable, return a built-in
   fallback WebP and the default display duration.
5. Save the response and next-entry state together, then return the response.

Support one outstanding request per device. Keep a small bounded history of
recent request IDs so delayed older requests can return `409` instead of being
treated as new advancements. The device should discard responses for old IDs.
Exact retry replay is guaranteed while the process is running; document that a
server restart resets rotation/replay state in the initial version.

Keep `GET /api/current` temporarily as a compatibility route for one explicitly
configured legacy device. It retains advance-on-request behavior and cannot
provide retry deduplication. Remove it only after the firmware migrates.

Provide a separate preview operation that renders a specific app instance and
never changes rotation state.

### Playlist changes

On add/remove/reorder/enable changes, increment the playlist revision. Preserve
the next entry when its ID still exists and is enabled; otherwise select the
first enabled entry. An in-progress response uses its original playlist snapshot.
A retry of that response still returns its saved bytes.

## 2. App interface, freshness, and failures

### Problems

- `App.py` uses unrestricted `Callable` and `dict` types, hiding required fields
  and allowing incompatible fetch/render pairs.
- `None` means both a failed fetch and a valid absence of content.
- `Carousel` calls `update()`, then `App.render()` may call it again after a failed
  fetch. Empty dictionaries are also treated as missing caches.
- `clock_update()` returns a dynamic TTL inside its data, but `App` ignores it.
- `App.render()` does not consistently check freshness when called directly.
- Only source data is cached; every selection redraws and re-encodes the WebP.
- Failed refreshes have no backoff or maximum acceptable data age. Old flight
  information can remain visible indefinitely.
- MTA caches calculated wait minutes, so those values do not count down between
  source refreshes. Its stations and lines are globals rather than settings.
- Flight selection uses global location settings rather than instance settings.

### Fix

Define typed contracts in the shared app model/runtime modules:

- `fetch(config, fetch_context) -> FetchResult[Data]`
- `render(data, render_context) -> RenderResult`

`fetch_context` supplies provider access and the current time. `render_context`
supplies display dimensions, the current timezone-aware time, and drawing assets.
Render functions must not fetch network data or mutate runtime caches.

Use Pydantic configuration models for validation and future API schemas. Use
dataclasses or typed models for normalized source data. Bind matching config and
data types through a generic function adapter rather than passing arbitrary
dictionaries. If class-based apps become useful later, describe the same contract
with a `Protocol`; do not add an inheritance hierarchy just for consistency.

`FetchResult` must distinguish:

| Status | Meaning | Runtime action |
| --- | --- | --- |
| `ok` | Valid data | Replace data cache and schedule its next refresh |
| `empty` | Successful response with no relevant content | Clear obsolete data and schedule another normal refresh |
| `error` | Timeout, provider error, or invalid response | Apply backoff; use prior data only within the app's maximum stale age |

Include the next refresh delay and an internal error description in the result.
Advance successful-fetch bookkeeping for both `ok` and `empty`. Track retry time
separately from the time of the last successful data fetch. Treat unexpected app
exceptions as errors and log them with the app instance ID.

`RenderResult` contains a frame sequence and an optional next render deadline.
The frame sequence contains same-sized images, positive frame durations, and an
explicit playback policy: repeat or play once and hold the final frame.

### Runtime implementation

Provide one operation, `get_frame(instance, display_profile)`, that:

1. Refreshes missing/due data at most once, under a per-instance lock.
2. Applies the explicit empty/error policy.
3. Reuses cached WebP bytes when their data, configuration, dimensions, and
   rendering deadline are still valid.
4. Otherwise renders and encodes once, then atomically replaces the output cache.
5. Returns displayable output or an explicit unavailable result to the carousel.

Use monotonic time for in-process deadlines and retry delays. Use timezone-aware
wall-clock time for clock values and provider timestamps. Convert the difference
to a wall-clock rendering boundary into a monotonic deadline when caching.

Invalidate both caches on configuration changes, including requests already in
flight: discard a completed fetch/render if its configuration revision is old.
Include a renderer version in output-cache identity so rendering changes cannot
reuse incompatible cached output.

Initial app policies:

| App | Refresh/render behavior |
| --- | --- |
| Clock | Calculate time locally; invalidate output at the next minute boundary; timezone and supported presentation options come from instance config |
| Weather | Refresh source data every 600 seconds; reuse output until data/settings change; allow stale data for at most 30 minutes |
| MTA | Refresh feed every 30 seconds; retain arrival timestamps and calculate waits at render time; expire output at the next displayed wait change, capped at 30 seconds; allow stale feed data for at most 90 seconds |
| Flights | Refresh every 120 seconds initially; a valid empty result makes the instance unavailable; expire old data after 120 seconds rather than retaining an old aircraft during outages |

Treat these as initial policies to validate on the display, not provider guarantees.
Use exponential error backoff starting at 5 seconds and capped at 60 seconds.
Backoff does not extend the maximum stale age. A first-load failure returns
unavailable immediately after the bounded fetch attempt; it does not fetch twice.

Move weather location/units, MTA stations/lines, and flight location/bounding box
into each app's config model. Construct provider URLs inside the implementation.
Keep credentials out of serialized instance settings and error responses.

## 3. Request execution and provider access

### Problems

- Async routes call synchronous `requests` and Pillow operations directly,
  blocking the event loop.
- Provider requests have no explicit timeouts and inconsistent status/parsing
  checks. Flights can make an unbounded number of sequential enrichment requests.
- Adding concurrency without locks would allow duplicate refreshes and competing
  rotation updates.

### Fix and strategy

Keep fetch/render functions synchronous for the first refactor. Run the whole
device-serving operation in FastAPI's thread pool through a synchronous route or
explicit offloading. Do not simply mark synchronous helpers `async`.

Use a common provider request helper with explicit connect/read timeouts, status
checking before parsing, and consistent error mapping. Start with 2-second connect
and 3-second read timeouts. Limit flight enrichment to the three nearest eligible
aircraft and enforce an overall fetch budget of 8 seconds by calculating the
remaining deadline before each request. Validate these budgets against actual
provider behavior. Do not add automatic HTTP retries on top of runtime retries.

Use separate per-device and per-instance locks. Never acquire a device lock from
inside an app runtime, and never hold two instance locks at once. This keeps lock
ordering predictable. Pre-render the fallback image at startup.

One slow provider should affect its requesting device, not block the entire API.
Add background refresh only if measurements show on-demand fetch latency is a
problem. Multiple workers require shared rotation/replay state before deployment;
SQLite configuration persistence alone does not solve that.

## 4. Drawing toolkit

### Problems

- `Text.coords()` handles bounding-box offsets, but text placement has no stated
  contract for bounds versus baseline alignment.
- Each app repeats font loading, margins, positioning, buffer creation, and WebP
  encoding. Font paths depend on the working directory.
- No referenced custom font files are present under `apps/api`; fallback fonts
  change measurements and appearance. The clock's small PM font also loads
  outside its primary fallback handling.
- Weather recreates text buffers during each animation frame.
- Long airline names and other strings have no explicit overflow policy.
- Some drawing functions accept a background color but do not apply it.
- Old app-specific drawing functions remain duplicated in `utils/draw.py`.

### Fix

Create a small `graphics/` package with these modules:

| Module | Public behavior |
| --- | --- |
| `geometry.py` | Integer `Rect(x, y, width, height)`, inset, centering, region splits |
| `canvas.py` | Canvas creation, background, basic shapes, layer compositing, clipping |
| `text.py` | Text measurement, bounds/baseline drawing, text layers, overflow policies |
| `assets.py` | Package-relative font/icon loading, validation, cached assets |
| `animation.py` | Frame sequence, reveal/blink helpers, repeat/hold policy |
| `webp.py` | Shared static/animated WebP encoding and output validation |

Specify these coordinate rules and test them:

- `(0, 0)` is the top-left canvas pixel; dimensions and positions are integers.
- Rectangles use exclusive right/bottom edges. Translate to Pillow's conventions
  inside the wrapper, so app code does not add/subtract one inconsistently.
- Bounds placement aligns the measured glyph rectangle inside the target region.
- Baseline placement uses stable font ascent/descent or an explicit baseline, so
  changing characters do not move a row vertically.
- Exact illuminated-pixel placement is an explicit option using a rendered alpha
  mask's nonempty bounds; it is not assumed equivalent to Pillow's text bounding box.
- Text advance is separate from bounds width when positioning adjacent segments.
- Clip all drawing to the requested region. Choose a documented integer rounding
  rule for centering odd-sized objects.

Text drawing must support an explicit overflow policy. Implement clipping and
truncation first; add wrapping/scrolling only when an app needs them. Return
placement metrics to callers that need to position adjacent elements.

Bundle the intended fonts in `assets/fonts/` and validate them at startup. Make
fallback selection explicit and consistent. Cache fonts by asset/size and icons
by asset/size/resampling policy; treat cached assets as immutable. Preserve alpha
when compositing icons. Use nearest-neighbor resizing for pixel-art assets.

Render weather's text/icon layers once, then animate clipping of those layers.
Keep clock layouts, subway badges, and weather/flight compositions in their app
modules. Do not move domain-specific renderers into the shared graphics package.

Centralize WebP encoding. Start with lossless output and measure encoded size and
ESP32 decode performance. Validate canvas size, equal frame dimensions, durations,
and output size before serving. Measure the device's available memory and set an
explicit maximum payload size; do not invent a limit without checking the board.

Delete the deprecated app drawing functions after all imports use the toolkit.
Remove ignored drawing arguments or implement their documented behavior.

## 5. Firmware timing contract

The firmware changes are in `../hdk`, but must accompany the new device endpoint.

### Problems

- `main.cpp` waits 10 seconds after each fetch, so the interval includes request
  time and does not use a server-provided display duration.
- `graphics.cpp` checks for new content only after a complete animation playback.
- The weather WebP has nine 100 ms frames and a 10,000 ms final frame: approximately
  10.9 seconds per playback.
- The graphics task restarts playback without honoring the encoded loop policy.

### Fix

- Send device ID and request ID using the new endpoint. Preserve the request ID
  across failed downloads/decodes and retry without advancing.
- Validate and prepare new graphics before reporting acceptance to the fetch task.
  Keep the previous valid graphic if preparation fails.
- Check for replacement content between animation frames and while waiting for a
  long frame duration. Use an interruptible wait rather than sleeping through an
  entire final hold.
- Support repeat and play-once/hold-final policies. Hold-final must still respond
  to replacement content.
- Start the display-duration timer when the graphics task activates the new image,
  then request the next item after that duration. Network latency may extend the
  previous item's dwell time; it must not shorten it.
- Remove weather's hard-coded 10-second final hold. Its entrance animation should
  finish and hold the final frame until replacement; playlist duration controls
  when the device requests replacement.

## 6. Configuration and future web endpoints

After device isolation and runtime contracts work, add SQLite storage for device
configs, app instances, ordered playlist entries, and revision numbers. Keep locks,
provider clients, monotonic deadlines, and image bytes out of configuration storage.

Add these API operations over the same service used by device requests:

- List available app definitions and their configuration schemas.
- Read/update a device's playlist, including order, enabled flags, and durations.
- Create/update/delete configured app instances, with validation and cache
  invalidation. Reject deletion of a referenced instance unless its playlist
  entries are removed in the same transaction.
- Preview an instance using a device's display profile without rotating it.

Use revision checks to reject conflicting edits. Keep configuration updates
transactional. Device ID identifies a device; it is not an authentication secret.
Choose access control before exposing management endpoints outside the trusted
development environment.

## Implementation order

1. **Typed app contracts and runtime:** Introduce result/config/data models and
   the function adapter. Migrate all four apps. Preserve the existing endpoint
   while fixing refresh, empty/error handling, and duplicate fetches.
2. **Independent playlists:** Replace singleton instance registration with app
   definitions. Build per-device instances, playlist selection, fallback behavior,
   and request-ID replay. Add the new device endpoint and isolated preview path.
3. **Drawing toolkit:** Bundle fonts; implement geometry, text, assets, animation,
   and encoding. Migrate weather first, then clock, MTA, and flights. Remove old
   drawing functions once there are no remaining callers.
4. **Firmware integration:** Implement device/request IDs, response headers,
   interruptible playback, acceptance notification, and display-duration timing.
5. **Persistent settings:** Add SQLite configuration storage, revision checks,
   and management endpoints. Seed defaults matching the existing location/stations.
6. **Documentation and deployment:** Correct README behavior, document endpoints
   and single-worker limitations, and remove legacy routes when devices migrate.

Each step should remain runnable. Do not simultaneously introduce a job queue,
multi-worker deployment, or a new rendering library.

## Acceptance checks

Use fake providers and an injectable clock for automated checks. Avoid real API
calls in tests.

- Two devices independently receive the full configured sequence.
- Retrying a completed request ID returns identical bytes and does not advance.
- Concurrent duplicate requests fetch/render/select only once.
- Disabled, removed, empty, and failing entries follow the defined selection rules.
  Empty playlists return a valid fallback WebP without looping indefinitely.
- A successful empty flight result clears old aircraft data. Errors do not display
  data past the maximum stale age. Backoff prevents repeated immediate fetches.
- The clock changes at the minute boundary. MTA waits decrease without requiring
  a provider fetch and do not show arrivals that have passed.
- Configuration changes invalidate the correct caches and discard obsolete work.
- Preview requests never change any device's next entry.
- Unchanged weather data/settings reuse encoded bytes. Rendering deadlines expire
  time-sensitive output even when source data is unchanged.
- All static/animated outputs decode, have the expected dimensions and frame
  timing, and satisfy the measured device payload limit.
- Drawing checks cover bounds and baseline alignment, odd-size centering, clipping,
  truncation, descenders/accents, transparency, and long airline names. Compare
  rendered/decoded pixels, not compressed WebP bytes.
- Manual ESP32 checks verify animation replacement during a long hold, retry after
  interrupted downloads, final-frame holding, and configured display duration.
- Record fetch/render latency and encoded sizes for all four apps. Use those
  measurements to decide whether background refresh or a different encoder setting
  is necessary.
